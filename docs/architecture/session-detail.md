# Session detail (diary)

The session detail opened from History: stats, notes, graphs, the what-if threshold panel (#50) and the band breakdown. Hard rules are summarized under **Invariants** in [CLAUDE.md](../../CLAUDE.md); this file holds how the subsystem works and why.

## Detail screen

- **Diary detail** (`diary_screen.py`): Session stats, notes/tags/mood, graph tabs (metrics/raw/freq). Opened only from History (`show_session_detail(session)`), with back button, titled by `session_title` like its row (one line, cut with an ellipsis); its stats grid is Duration, the `session_score_rows` rows, Time Above Threshold, Longest Streak and Mood Rating (`_set_detail_rows`, like the end card's) (Avg Meditation, Avg Shamatha and Time Shamatha ≥ 90 were dropped from the cards — still stored, exported and used by the calendar; the one average a card shows is the scored metric's); the old session list above it (always hidden, rebuilt from every session on every notes save) is gone. **Notes are never lost** (#40): `show_session_detail` snapshots the fields as shown (`_saved_notes_state` — what the widgets show, not the row: an unrated session's slider shows 3), and `on_pre_leave` → `flush_notes()` saves the fields that differ (`_changes()`) — Back, a bottom-nav tab and Android back are all screen changes, so one hook covers them; `_flush_on_leave` (on_pause / on_stop) flushes it while it is the current screen — only then, since leaving already tried, and a retry on every pause repeated a failed save's error (e.g. for a session deleted since). Leaving sends only the changed fields, so it can't rate an unrated session; **Save Notes** sends what the screen shows, mood included (so an unrated session can be saved as 3). A successful save moves the snapshot; a failed one stays pending and is retried on leave. Per-session custom-formula series are **replayed**: the load worker (`_load_session_detail`) runs `_compute_session_formulas`, which rebuilds the evaluators from the session's recorded `custom_formulas` JSON and recomputes their series via `recompute_formula_series` over the rows it already read; `detail_graph_data(rows, series)` puts them in place of the stored custom_formula_* columns, and the metrics graph's fill step calls `set_session_formulas(series, names)` first, which names the series. **Try another threshold** (#50, the what-if): `WhatIfPanel` (`app/ui/widgets/what_if.py`) under the stats grid — threshold controls (a slider, ±5) and Reset over the time above threshold and longest streak at them, view only: one control for a simple session, one per segment for a program. The engine is `app/session/what_if.py`: `scored_ticks(session, rows, formula_series)` gives each tick's value and recorded target and the `Segment`s the controls move — for a simple session one segment over every tick, its value from the stored per-tick record (#83) when every row has one, else from an older session's saved metric (its stored column, or the formula replay's series for a formula slot; meditation for a row from before #51, which is what its recorded numbers were measured on) at `threshold_used`; for a program one segment per program segment, each with the metric `program_plan` gives it, its target as the live session reads it (`segment_target`: a whole number, 50 when missing or unreadable — the graph's steps, the live goal and the start's threshold use it too) and a custom formula's `name`, a segment the session never reached dropped. A segment starts where the per-tick record shows the live session switching to its metric and target (it switches on elapsed time, and `_tick_loop` drops an overrun tick, so the switch drifts off minutes x 2; searched from the last switch found; a segment like the one before it can't be told apart, so it starts its minutes after it, capped at the next switch found — a segment left with no tick is dropped, and the rest keep their program `index`, which numbers their titles), else by its minutes as the graph's steps are (`SessionProgram.threshold_steps(2)` — never the row timestamp, which is the EEG stream's clock). Values come from the per-tick record, else from the stored columns and the program's formulas run over the whole session by the `replay_formulas` callable the load worker passes (`recompute_formula_series` over the rows it read; the engine calls it only when there is no record, with `program_evaluators`) — every released build evaluates a program's formulas on every tick from the start. The 21 h of pre-release code before e71969b (2026-06-26) armed a fresh evaluator at each custom segment, so an `avg()` window restarted there: one dev-DB session recorded then replays 2 s off, and isn't special-cased. None when it can't be replayed: a formula the replay couldn't rebuild (its stored `custom_formula_*` column is stale), a program that can't be read or has no tick. `rescore(ticks, overrides)` re-runs the live accrual (`GoalAccrual`) with each segment's ticks against its override, or with None against their own recorded targets — so as recorded gives back the recorded numbers by construction (known-answer tests against the real `SessionManager`; measured 2026-10-08 on DB copies: every session of the phone's, and every dev-DB session but pre-release ones — 138 above, and 19 from March 2026 that stored a streak of 0 from before streaks were recorded or rows that don't match their duration) — the whole session's streak carrying across a boundary, a segment's staying within it; `per_segment=False` skips the segments' own stats (a simple session's recompute: ~1 ms for 3 h on desktop). `line_steps(ticks, overrides)` is the graph's line: each moved segment's value from its start, an untouched one's recorded steps clipped to it. The panel starts as recorded and a moved control applies its threshold to every tick of its segment; recomputes are coalesced to one per frame (`Clock.create_trigger`). A program's segments are titled `<n> · <metric> · recorded <target>` (`DiaryScreen.set_what_if`: n from the segment's `index`, the name through `SERIES_NAMES`) and show their own `Above · Streak`; the totals under them are titled `Whole session` (attached for a program only). The load worker builds the ticks in their own guarded step after the graph data — a row it can't score fails only the panel (`show_what_if_failed`), not the graphs — and the panel's fill step runs last, so it can keep the metrics graph's recorded line (`threshold_steps`, a read accessor), which Reset puts back. A slider's range covers its segment's values and recorded targets (a formula can go below 0 or past 180); the graph draws a threshold outside its 0–scale range on its floor or ceiling, as it draws such values. A session it can't rescore gets a message in place of the controls ("This session can't be replayed."), as do the open ("Loading…") and a failed load; the line under the title ("Recorded at <targets> · nothing is saved", or for a program "Each segment starts at its recorded target · nothing is saved") goes with the controls; every message state clears the session from the panel (and its segment controls: a late value from one is ignored) and disables Reset, which sits in the always-attached header — Reset while the next session loaded put the last one's line on its graph. The chevron right after the title (`_btn_collapse`, History's `theme.FoldChevron`) folds the body away, detached — whichever of the controls or the message it shows comes back on unfold, and a session or message set while folded stays folded — with Reset left in the header; saved per profile as the registry setting `what_if_collapsed` (`DiaryScreen.what_if` exposes the panel).

- **Only the shown tab's graph draws**: `_switch_graph_tab` enables drawing on the shown graph and pauses the others (`set_drawing_enabled`; enabling redraws), as the live screen's `_set_view` does for its hidden view — so a fit, a data load or a theme switch costs nothing on the hidden tabs. The three tabs are one zoom group (see [graphs](graphs.md)).

## Loading

- **The session detail opens at once** (#59): `_on_session_select` shows it in the tap's frame from the row History holds (`HistoryScreen.session_by_id` — `get_all_sessions` is `SELECT *`, and notes and renames update it in place): title, stats and notes, editable at once, with no full-screen spinner. Its band totals and graphs show a non-modal "Loading…" (`_band_placeholder`, `_graph_placeholder`; `DiaryScreen._ready` holds the sections whose data is in) while the worker `_load_session_detail` reads the band totals (one `SUM` query, sent first), then the metric rows **once** — the formula replay runs over the same rows (`_compute_session_formulas(sid, session, rows)` → `recompute_formula_series(..., rows)`; it used to read them a second time) — and builds each graph's series, the raw-EEG tail and the markers off the main thread (`diary_screen.detail_graph_data`, pure). `_fill_detail(token, steps)` then puts one section in per frame (`Clock.schedule_once(…, 0)` from a callback runs next frame), the shown tab's graph first (`graph_fill_order`), through `DiaryScreen.fill_graph`. Every open takes a load token (`_detail_load`): a result for an earlier open, or for a detail no longer on screen (Back, another tab), is dropped, so opening B right after A shows only B. A failed load reports `session_detail_load_failed` and the sections say "Couldn't load this session's data." — the stats and notes keep working. `load_metrics_preview(rows)` is the same builder and fills, synchronously (tests, `_inject_session_formulas`). Desktop, a 2-hour session (14,400 ticks): on screen after 1.72 s behind the spinner → 0.07 s; the metrics graph filled after 1.52 s; the longest frame 93 → ~73 ms (the open frame itself); the metric-row read (`SELECT *` into dicts) is now nearly all of the wait. DB reads off-thread are safe (`check_same_thread=False` + WAL).
- Diary raw-EEG `_synthesize_waveform` synthesizes only the **tail** the graph retains (`_RAW_MAX_SAMPLES = sample_rate*60`), starting the global sample index at the first kept tick so the tail is phase-identical to a full synthesis; returns `(waveform, start_tick)` so raw markers map tail-relative. Avoids computing ~99 % discarded samples on long sessions (3.6 s → 75 ms for 47 min).

## Band breakdown

- **Per-band power breakdown** (issue #8) — the diary detail shows total power per frequency band over the whole session via `BandTotalsView` (`app/ui/widgets/band_totals.py`): a **sortable table** of band-colored share bars + Power and % columns, with a **Detailed (8 sub-bands) / Grouped (5)** toggle. Computed **on read** — `DatabaseManager.get_session_band_totals(session_id)` runs one `SELECT SUM(<band>_raw)` over the already-recorded per-tick band powers, so there's **no schema change** and the live tick path is untouched. Grouping and sorting are pure view transforms: `grouped_totals(totals)` (alpha1+alpha2→alpha, etc.) and `band_rows(totals, mode, sort_by, descending)` build the ordered rows; `band_shares`/`format_power` are unit-tested too. Tapping a column header (`_HeaderCell`, a `ButtonBehavior` label) sorts (`band`=frequency order, `power`/`percent`=magnitude); tapping the active column reverses. The active column's sort arrow uses the **MDI `Icons` font via Kivy markup** (geometric ↑↓ render as tofu in this Roboto build — same constraint as the `»` legend marker). View state (`mode`/`sort`/`desc`) persists per user as the JSON setting `band_breakdown_view`: the widget's `on_change` → `diary_screen.band_view_persist_cb` → `AppManager._persist_band_view`; restored when the detail opens (`_on_session_select` → `set_band_view_state`), before the totals arrive. Fed from the detail's worker, first: `_load_session_detail` → `set_band_totals`. The live end-summary deliberately does **not** show it (fixed, full layout).

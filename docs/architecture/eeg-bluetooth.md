# EEG sources and Bluetooth

How EEG data reaches the app: the mock and NeuroSky streams, the Bluetooth link and its reader lifecycle, the BT wait at session start, and the diagnostic tools. Hard rules are summarized under **Invariants** in [CLAUDE.md](../../CLAUDE.md); this file holds how the subsystem works and why.

## Sources

- **EEG sources** (`app/eeg/`): `mock_stream_v2.py` (active mock with frequency-based synthesis, NeuroSky-compatible format), `mock_stream.py` (legacy mock), and `neurosky_stream.py` (real Bluetooth RFCOMM / pyserial, ThinkGear protocol). Both active sources produce 8 band powers + raw 512Hz waveform + eSense attention/meditation. Desktop BT falls back to PyBluez if `socket.AF_BLUETOOTH` is missing (common in PyInstaller bundles). Real stream tracks `_last_packet_time` for stale data detection and parses battery level (code 0x01, though TGAM hardware doesn't send it). BT connection kept alive between sessions to avoid RFCOMM/EBUSY issues; `reset_sample_state()` clears cached values for new sessions.
- **The bands** (`app/eeg/band_spec.py`): one table of the 8 bands in the order `ASIC_EEG_POWER` (0x83) sends them, each with the app's name (Alpha 1 for NeuroSky's "low-alpha", matching the custom-formula variables) and its range from the ThinkGear Communications Protocol (delta 0.5–2.75 Hz … gamma2 41–49.75 Hz), plus the 5 grouped bands, each spanning its sub-bands (the hardware's bands leave gaps: 9.25–10, 16.75–18 and 39.75–41 Hz). `neurosky_stream.BAND_NAMES` takes its order from it; the band table and the live and diary band graphs take their names, and their 5-band sums (`group_powers`), from it. The mock's `BAND_FREQ_RANGES` (`mock_stream_v2.py`) are its own invented synthesis bands, not these. The metrics engine and the database still list the 8 keys and the alpha1+alpha2 groupings themselves, and each screen keeps its own band colours.

## Connection

- NeuroSky Bluetooth uses pyjnius on Android, Python socket BTPROTO_RFCOMM on Linux (with PyBluez fallback), pyserial over virtual COM port on Windows. BT connection is kept alive between sessions (not closed on session stop) to avoid RFCOMM EBUSY and ThinkGear reinit failures. On app exit, the socket is NOT explicitly closed — the kernel handles cleanup while BlueZ may keep the ACL link for faster next-launch reconnect. Connection timeout is 30s, signal wait is 8s. Stale data (no new packets for 10s) auto-stops the session.
- BT auto-connect picks the single matching MindWave automatically. When more than one paired device matches the `mindwave`/`neurosky` name filter, the auto-scan and start-session paths route the user to Settings → Device, expand the section, scroll it into view, and surface a "pick one" banner with only the matching devices listed. The banner is cleared by `update_device_status(connected=True)`. Helper: `EEGMeditationApp._filter_mindwave`; UI hook: `SettingsScreen.focus_device_section(message)`.
- **The link is always to the selected headset.** It stays open between sessions, so `NeuroSkyStream.set_device` to another address stops the reader first; otherwise the next Start would reuse the old headset's socket and record its session under the new headset's name. Every target change goes through it: a pick in Settings, a profile's saved headset on load, the wizard and the start-time auto-select. A pick is refused while a session runs or connects (`_on_device_select` → `_refused_while_session_runs`), as a profile switch already is. Settings' row marks rely on this: the connected headset is the selected one while `is_connected` (`AppManager._device_state()`).

## Reader lifecycle and the BT wait

- **The MindWave serves one RFCOMM channel — a connected socket nobody drains stalls its transmitter until the headset is power-cycled**, so `NeuroSkyStream`'s reader lifecycle must never orphan one, and **at most one reader thread may exist**. That single-reader invariant is the real guarantee: readers share `_bt_socket`/`_running`/`_connected`, so with two alive a late reader's `_adopt_socket` overwrites the live one's socket reference and its failure path kills the live session — the epoch check cannot prevent that. `start()` bumps `_connect_epoch`, passes it to `_read_loop(epoch)` and **returns a bool**: False (with `_last_connect_error` set) when refused — no device, or a previous reader still alive ("Previous connection is still closing"). `stop()` sets `_stop_event`, bumps the epoch, and closes the socket **before** `join(_STOP_JOIN_TIMEOUT=5s)`; the close interrupts **every** blocking point: Android `connect()` (`_run_connect_attempts` publishes each socket as `_pending_socket` before `connect()` and re-checks `_running` after publishing, so `stop()` either closes it or the reader sees the stop; `BluetoothSocket.close()` from another thread aborts `connect()`), Android read (socket close), desktop `connect()`/`recv()` (`_shutdown_before_close` → `shutdown(SHUT_RDWR)` on native and PyBluez sockets — on Linux a cross-thread `close()` alone doesn't wake them), serial read (`select` 0.5 s poll — a cross-thread `os.close()` doesn't wake `os.read()`), and the back-off sleeps (`_stop_event.wait`). An aborted connect raises instead of falling through to the next method, and the superseded reader returns quietly without writing `_last_connect_error`. A headset-off connect chain is ~3×7.7 s on-device, so without the abort `stop()` froze the main thread for the full join. If the join still times out, `stop()` **keeps** `_thread` so `start()` refuses (nulling it let a second reader start); it joins a local copy because the tick thread and the main thread can both be in `stop()`. `_close_socket` runs under `_close_lock` (stop() and the exiting reader both call it). A single late reader (epoch superseded after its connect returned) closes its socket instead of adopting it; `_last_connect_error` is cleared only after that check; and the reader clears `_connected` on exit, so a stop() landing just after `_connected = True` can't leave `is_connected` stuck True with no reader (which made the next Start "reuse" a dead connection). Every failed Android connect attempt (secure → insecure → `createRfcommSocket(1)`) closes its socket; the ch=1 fallback is called directly on the device — the former `Class.getMethod` reflection hit a pyjnius varargs error and never reached Bluetooth. In `app_manager`, `_begin_bt_wait()` checks `start()`'s result **before** entering the wait: a refusal releases the wake lock/keep-alive service and shows an honest retry overlay, with no `bt_connect_failed` soft-error (whose 60 s cooldown would otherwise hide the next real failure). **All five BT-wait exits** (Cancel, Stop, no-data, failed connect, timeout) go through `_abort_bt_wait()`, which stops the tick watcher (and clears `_waiting_for_bt`/`_bt_signal_start`) **before** `_real_stream.stop()`, then releases the wake lock and keep-alive service — the watcher reads `not stream._running` as a failed connect, so the old stream-first Cancel produced a false "Connection failed" dialog, and the failed-connect exit used to leak the wake lock and foreground service. **A session start is one attempt** (#52): `_start_attempt` advances on every Start (`_on_start`) and on every ending — `_undo_session_setup()` advances it, and every ending goes through it — and a callback queued for an attempt does nothing once it has moved on: the device scan's result in `_on_start`, and every main-thread callback of the BT wait, which `_handle_bt_wait` queues through `_on_main_for_wait` (the "connected" UI + audio `_on_session_connected`, the three exits' retry screens, the countdown text). The wait's attempt is `_wait_attempt`, taken on the main thread in `_begin_bt_wait` — not read by the tick thread when it queues, because a Cancel can land while the tick is mid-tick, and its 1 s join can time out (`read_sample` waits for the reader's lock), so the tick may queue after the Cancel has finished. A Cancel during "Scanning for MindWave…" used to start the session anyway; a Cancel or an active-profile delete in the frame the first data arrived left a zombie (noise playing, idle controls, no tick, Restore refused); a wait exit's queued retry screen could undo the next Start. `_on_stop` decides by `SessionManager.state`, not `_waiting_for_bt` (a wait exit clears the flag before its idle UI is shown, so a Stop in that window offered to save a session that never started): RUNNING/PAUSED asks to stop and save, FINISHED (the timer ended it on the tick thread; its teardown is queued) is ignored — cancelling there stopped the kept-alive headset link — and anything else cancels the start (`_cancel_session_start`). Every ending — `_finalize_stop_ui`, a cancelled start, a refused connect and the three tick-thread wait exits (their queued callbacks) — undoes the start's setup through the one `_undo_session_setup()` (program series and state via `_restore_program_series`, the training marker, the shamatha pill, timer and session manager reset, wake lock and keep-alive service; the releases are idempotent): a cancelled program session used to leave `_session_program_active` and the program series snapshot behind, which a later simple session then persisted over the user's series selection. A kept-alive connection's start shows the same `_on_session_connected` as the wait's; the header's start time and the graph's wall-clock axis come from `SessionManager.started_at`, not from when the queued UI ran (after a screen lock, the unlock time). If a Cancel's join times out, the late tick can still start `SessionManager` after the Cancel's reset; only its UI and audio are gated. `_waiting_for_bt`/`_bt_signal_start` are initialized in `__init__` (Cancel before any Start used to raise `AttributeError`). **Each connection gets its own windows**: when the wait sees the link drop while the reader reconnects, `_handle_bt_wait` restarts both the no-data window (`_bt_signal_start`, `_BT_SIGNAL_TIMEOUT` 8 s) and the connect window (`_bt_connect_start`, `_BT_CONNECT_TIMEOUT` 30 s) and records `_bt_dropped_at` (monotonic), so a reconnected socket gets its full time and only packets after the drop count as streaming — and the session starts only on band data with a packet on this connection (`total > 0 and has_packets`: the reader keeps the last band values across a reconnect); the 30 s from Start used to end a wait whose link dropped after it (a sensor placed slowly, or a slow first connect). Restarting them unbounds a headset that keeps connecting and closing, so a wait ends at its third drop (`_BT_MAX_DROPS` = 2, `_bt_drops` reset per wait) with "keeps closing the connection"; that exit and the no-data one share `_give_up_bt_wait(name, message)`. On the phone (2026-10-06) the headset closed a fresh socket without sending a byte, the reader's reconnect succeeded, and the wait gave up 0.4 s later on the old socket's elapsed time, closing the new socket; a packet from before a drop also used to read as "streaming" and kept a silent new socket's wait open with no timeout. `tests/test_bt_wait_reconnect.py` replays those timings on a fake clock. Android reads are one bulk `InputStream.read(buf, 0, n)` per chunk, the buffer sized to the read (pyjnius marshals the whole array both ways, so a reused oversized buffer is slower), replacing ~4000 byte-at-a-time JNI calls/s at the 512 Hz raw rate; the reader thread runs at Android priority −8 (the NeuroSky SDK reader's MAX_PRIORITY). `_log_throughput` logs `BT throughput: N B/s, N B/read, backlog high-water N B` every 30 s. Healthy is ≈4132 B/s (512 raw packets × 8 B + one 36 B eSense packet per second); a high-water that keeps rising means the reader is losing. A flat ~2 KB high-water during a live session (≈0.5 s stalls from ~60 s in) tracks Kivy rendering: it vanished for a whole screen lock while the tick thread and DB kept running (measured 2026-09-26) — the main thread holding the GIL during graph redraws. `app/ui/render_stats.py` measures it: every `ScrollableGraphWidget._redraw` is timed per `graph_id` (the drawing itself is `_draw`) and a per-frame `Clock` callback (started in `on_start`) tracks the longest gap between frames, ignoring gaps over 5 s (a suspended loop); every 30 s — the same cadence as `BT throughput` — a window that had redraws logs `Render: frame gap max N ms | <graph_id> Nx avg N max N ms | …`. Measured 2026-10-01 (11-min live session, headset on, Metrics view): the **live metrics graph** is essentially all of it — redraw avg rises 18 → ~63 ms over the first ~2.5 min and then stays flat (max ~160–180 ms, at 2 Hz ≈ 13% of the main thread), the raw and band graphs measure ~0 ms; frame gap max ~210 ms, and the BT high-water doubled (≈300 → ≈600 B ≈ 145 ms of data at 4132 B/s) in the same window the redraw max jumped. So high-water ≈ longest frame gap × throughput: no data loss (throughput steady), but each long redraw is a visible UI hitch, and making `ScrollableGraphWidget._draw` cheaper is the lever (a 2 KB high-water ≈ a 0.5 s frame) — see **Graph drawing cost** in [graphs.md](graphs.md). `tests/test_neurosky_lifecycle.py` covers stop-during-connect, refuse-while-alive through the real `stop()`, `start()`'s status, concurrent `stop()`, the stale-`_connected` race, stop waking a blocked desktop `recv` and a silent serial read, connect abort, the successful adopt handover, and failed-attempt cleanup; `tests/test_bt_wait_abort.py` covers the watcher-before-stream order on every exit, the failed-connect wake-lock release, the refused-start path, and `__init__` defining the wait state.

## Diagnostic tools (`tools/`)

- `bt_test.py` — Minimal raw RFCOMM + ThinkGear parser for connection debugging. No Kivy, no threads. Usage: `python tools/bt_test.py [MAC] [seconds]` (default 30 s). Prints only the ~1 Hz packets (printing all 512 raw-wave packets/s stalls the reader and fakes dropouts) and ends with the single-byte codes the device actually sent (e.g. whether battery 0x01 ever appears).
- `ble_battery_scan.py` — BLE GATT service enumerator (requires `bleak`). MindWave Mobile 2 doesn't expose BLE on Linux/Android (iOS only).

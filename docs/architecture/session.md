# Session lifecycle

The session state machine, the tick thread, persistence through checkpoints (#30), the timer, and running through a screen lock. Hard rules are summarized under **Invariants** in [CLAUDE.md](../../CLAUDE.md); this file holds how the subsystem works and why.

## State machine and tick

- **Session lifecycle** (`app/session/manager.py`): Start/Pause/Resume/Stop state machine. Coordinates EEG stream, metrics engine, audio feedback, and database flush. Tracks `time_shamatha_90` (time shamatha score >= 90, independent of user threshold).
- Session tick runs in a Python daemon thread (`SessionTick`) instead of Kivy `Clock` so EEG compute, audio volume updates, and DB flushes continue while the Android screen is locked. UI updates are dispatched via `_on_main` (`Clock.schedule_once`); they queue during pause and drain on resume. **At most one tick thread**: two process every tick twice (the timer counts down at double speed, `add_metric`'s fixed 0.5 s per call inflates time above threshold / streak / time ≥90, twice the metric rows are saved and the live graph runs ahead of the clock). `_start_tick_thread` is a no-op while a tick thread is alive, and each thread gets its **own** stop event (`_tick_loop(stop)`; `_tick_stop_event` holds the current one) — a single shared event cleared on restart revived a thread whose `_stop_tick_thread` join (1 s) had timed out. `_cancel_stop` (Cancel in the Stop dialog) restarts the tick only for a RUNNING session: on a paused one the restarted thread was orphaned by the next Resume's start, which doubled every tick until the next Pause/Stop (on-device: timer 53 s while the graph read 1:35).
- Session names auto-generated as `"YYYY-MM-DD HH:MM - DeviceName"` (`start_stamp` of `SessionManager.started_at`) to distinguish mock vs real; older sessions carry `"HH:MM - DeviceName"`. Neither is shown raw: `app/ui/session_labels.py` composes what a session is called on screen (#49) — `session_title` (`"YYYY-MM-DD HH:MM - <label>"`, the date and time parsed from `date_time`, never sliced; just the date and time for an unnamed session), `session_label` (the name without the session's **own** start time — `start_stamp(date_time)` + `" - "`, or its `HH:MM - ` in older names, both made with the row's `date_time` — which is what the rename editor edits; a time the user typed into a name is part of the name, and saving the editor unchanged writes nothing, so a default name keeps its date). `start_stamp` is the one `YYYY-MM-DD HH:MM` format: `_make_session_name` writes it and the title recognises it, `session_stats_line` (`recorded_score`'s metric name and average, duration, `Streak` — no average for a program or a session with no scored tick, no streak when 0; a session that saved no metric keeps its pre-#49 content, `Shamatha <avg_shamatha> · <duration>`, with no streak), `session_score_rows` (the `(label, value)` rows above Time Above Threshold and Longest Streak: `Metric` + the metric's name, `Average` + its average and `Threshold` + the targets in force (`_targets_text`: `score_targets` joined by ` › ` — Roboto has no `→` glyph — more than three as first › … › last, `threshold_used` for a row from before #83) — no Average when no tick was scored — or for a program `Metric` + `<program> (program)` (just `Program` when it was unsaved) and `Threshold` + `Per segment`, with no average (one metric per segment), or, when no metric was saved, the old `Avg Shamatha` + `<avg_shamatha>` and `Threshold Used` + `<threshold_used>`; an average reads the same here and in `session_stats_line`, through `_average`); the session detail's Metrics legend marks the recorded series with `»` (`_scored_key`; a program's key matches no series, and no saved metric marks nothing) and `session_notes_line` (the notes' first non-blank line). History's rows and the session detail title both use them.

## Persistence

- **A session reaches the DB only through checkpoints** (#30): `_checkpoint_session(stats=None)` → `DatabaseManager.checkpoint_session(sid, stats, ticks, …)` inserts or updates the session row **and** inserts the buffered tick rows in one transaction (`_insert_session` / `_update_session_row` / `_insert_metrics`, the same SQL `save_session` / `update_session` / `save_metrics_batch` use), so a process killed at any point leaves the row and the data of one checkpoint, which agree. It runs at every snapshot point: the 60 s tick flush (`_flush_tick`), the final save (`_persist_session_data`, with the stop's stats), `_flush_on_leave` (on_pause / on_stop, while a session is running or paused) and both backup workers. The row used to be written once, at the first 60 s flush, and only rewritten at a normal stop — a session the app died in (a crash, an Android kill of the backgrounded app) kept ~1 min of stats over all of its data (reproduced: SIGKILL 150 s in → row 59 s, data 120 s; now 119 s / 120 s). A closed window was already saved whole: `on_stop` stops and saves a running session. `SessionManager.elapsed_seconds` is frozen at the pause while PAUSED (it returned the stop-time `_elapsed`, 0, so a checkpoint of a paused session wrote duration 0). Ticks since the last checkpoint (≤ 60 s) are still lost on a kill. `_record_tick` (the tick's `add_metric` + buffer append) and a checkpoint's snapshot of both run under the class-level `_checkpoint_lock`, so a checkpoint from the main or backup thread neither loses a tick nor writes stats that don't match its rows; a failed checkpoint puts its ticks back for the next one. Leaving the app and both backups go through `_checkpoint_or_report()`, which logs and reports a failure (`session_checkpoint_failed`) and carries on: the settings flush, the stop-and-save of `on_stop` and the rest of the backup still run. A pending marker is set on the tick's row before it is recorded. The row is dated and named by the session's start (`SessionManager.started_at`, 0.0 before a start and after `reset()` → `checkpoint_session(started_at=…)` and `_make_session_name`), not by its first save a minute later. Session persistence is split: `_persist_session_data(reason)` (tick-thread-safe DB write, no Kivy) + `_finalize_stop_ui(stats, id)` (main-thread UI teardown). `_stop_and_save` runs both on the main thread; the timer-expiry path runs `_persist_session_data` on the tick thread and defers `_finalize_stop_ui` via `_on_main`. **Every ending saves through this one path** (#39): user Stop is a themed `_confirm_action("Stop session?", ..., on_cancel=_cancel_stop)` whose OK is `_stop_and_save(reason="user")` — the old Save/Discard/Cancel popup and its drifted copy `_finish_stop` (which skipped `_restore_program_series`, `set_training_series(None)` and the mirror reload) are gone — and with them the Discard branch that lost a session: on a slow phone a Stop tap handled late (v1.4.0 froze for minutes redrawing a zoomed-out 3 h live graph) let the headset-off stale-data stop save the session first, then the late **Save** found no stats and ran the Discard branch's `delete_session` (reproduced on desktop, 2026-10-05); a confirm that arrives after the session has ended now writes nothing (`tests/test_session_ending.py::test_a_stop_confirmed_after_the_session_ended_another_way_keeps_it`). `_confirm_action`'s `on_cancel` fires on any close that isn't OK (Cancel, tap outside, Android back), so the tick that Stop paused is always resumed, and it decides **once**: Kivy keeps delivering taps to a `ModalView` during its 0.1 s fade-out, so a second OK (or OK right after Cancel) used to run the action again. That logic is `theme.confirm_popup`, the one confirm (OK left, Cancel right); `_confirm_action` and History's delete confirm both call it. The session-end card ("Session saved") offers **Save notes** (`_on_summary_save_notes`, card stays open), **OK** (`_flush_summary_notes`: saves notes that changed since the last save — so an untouched card writes nothing and clearing saved notes clears them — stops the gong, closes) and a low-emphasis **Delete session** behind a confirm (`_on_summary_delete` → `_delete_sessions`, which closes the card once the session is gone — a failed delete leaves the card and its typed notes); `on_pause` and `on_stop` both flush the card's notes with the settings through `_flush_on_leave`, skipped while `_restoring`. `_summary_saved_notes` tracks the last written text. Notes go through the one `_save_session_notes(sid, notes=, tags=, mood=)` (also the diary's Save and its leave-flush): `DatabaseManager.update_session_notes` writes only the fields given and returns whether a row changed, failures `report_soft_error`, success `_toast("Notes saved")` and `HistoryScreen.update_session(sid, ...)` — the History model's session updated in place, not a dirty reload (that started the list from the top after every edit); `_update_item` re-derives that row's item, so its notes line appears, changes or goes (and the row's height with it) at once — `_toast` is the one toast (also the double-back "Press back again to exit"): `C.TEXT` on `paint_panel`, added to the `Window` so it shows above any open popup, on every platform; only while the app is leaving (`_leaving`, set by `_flush_on_leave`, when nothing the app draws is seen) it is the native Android toast. `_delete_sessions(ids)` is the one delete (a History row, the History selection, the end card): one `DatabaseManager.delete_sessions(ids)` transaction (metrics and rows, so an error deletes none of them; `delete_session(sid)` is a selection of one; then a `wal_checkpoint(TRUNCATE)`, since one big transaction parks every deleted page in the WAL, measured 40–100 MB for a few hundred long sessions, which it keeps until a clean close; a failed checkpoint — e.g. "database table is locked" while another thread's read is open on the shared connection — is only logged, since the delete has committed) on a worker thread — a large selection took 0.3–0.8 s on desktop on the UI thread — behind the loading overlay, modal at once and painted only if it runs past 0.15 s (`show_loading(text, delay=0.15)`: a tap in that first moment reached the rows and the end card being deleted), reporting `on_done(ok)`; a `sqlite3.Error` is reported as `session_delete_failed`; on success the end card closes (and its gong stops) if it shows a deleted session — a notes save there then failed with "no such session" — and `HistoryScreen.remove_sessions(ids)`, which removes those rows and model entries in place (see the session list in [history.md](history.md)) — no rebuild, no spinner, wherever the user is. History never lists the running session: its row exists from the first checkpoint, with that checkpoint's stats, and a History reload (on opening it while it is dirty — from launch, every ending and a profile delete until it is next opened) listed it with them, frozen there until the next reload; `_refresh_history` drops `_current_session_id` while `_session_pipeline_live()`, and `_finalize_stop_ui` marks History dirty, so the session appears once it ends. `_delete_sessions` also refuses it (`_current_session_id` among the ids while live): deleting it left the next checkpoints writing ticks for no session.

## Timer

- Meditation timer is split: a headless `TimerState` (`app/session/timer_state.py`) drives the tick-loop countdown; all user-visible controls — enable, duration, custom-sound path, browse and test — live in the Settings → Timer accordion (`SettingsScreen`). When the timer expires (on the daemon tick thread), the order is: persist the session via `_persist_session_data(reason="timer")`, `AudioEngine.mute()` the noise (non-blocking), `_stop_tick_thread()` (safe from the tick thread — it skips the self-join — and clears `_tick_thread`, so `_session_pipeline_live()` is False once idle; a bare `_tick_stop_event.set()` there left Restore refused and the profile switch blocked after every timed session), `_on_main(_finish_on_main)` to defer `_audio.stop()` + `_finalize_stop_ui` to the main thread, then `play_timer_sound()` **last** (one-shot `MediaPlayer` gong, rings through lock). Persisting first and ringing last means a hung audio call can never cost the session or the summary. The gong plays until the file ends or the user taps the end card's OK or a confirmed Delete, each of which calls `AudioEngine.stop_timer_bell()` (releases the gong `MediaPlayer` on the main thread); `_start_session_common` also calls it pre-emptively to kill any long custom gong still ringing from a previous session.

## Screen lock and Android

- Android sessions hold a `PARTIAL_WAKE_LOCK` and run a foreground service (`service/session_keep_alive.py`, declared via `services =` in buildozer.spec) for multi-hour locked-screen operation. `SessionManager.stop(reason)` plays a short warble alert only for **failure** terminations (`stale_data`, `bt_lost`, `error`); `user` and `timer` are planned stops and stay silent (`timer` plays its own gong).
- After a session that ended during a screen lock, the live graph is reloaded from the session-lifetime mirror buffers via `_reload_live_graphs_from_mirror()` (used on both Android resume and finish) — the locked portion never reached the live graph through the per-tick `add_point`, so without this the graph would show only the pre-lock seconds while History shows the real duration.

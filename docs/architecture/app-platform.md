# App lifecycle, platform and build

The user gate and profiles, the Android back button, error reporting, test guardrails, and build/CI specifics. Hard rules are summarized under **Invariants** in [CLAUDE.md](../../CLAUDE.md); this file holds how the subsystem works and why.

## User gate and profiles

- **Hard user gate:** the app is never usable with no active user. `build()` gates on `resolve_startup_user(db)` (the resolved uid, or `None`) — NOT on `get_all_users()` emptiness, which let "users exist but `last_user_id` unresolved" (reinstall / restored DB / deleted-active-profile / corrupt `last_user_id`) slip into a usable-but-unset state. `None` → bottom nav disabled synchronously (no cold-start tap window) + blocking `_show_first_run_popup` (`self._gate_popup`, made un-escapable in `_on_keyboard`). Deleting the active profile re-enters the gate. Per-user handlers use `_require_user(action)` (surfaces a message, returns the uid or `None`) instead of a bare silent `return` — wired into `ProgramSettings.on_save`/`_save` (empty-name / no-user / saved-programs cap) and `on_load`/`on_delete`, `FormulaSettings.on_load`/`on_delete`, the series picker's saved-formula Choose. History/Diary go through `sessions_for_view(db, uid, show_all)`: the deliberate "Show All Users" view (`_view_all_users`, set only by `_on_user_switch(None)`) queries all sessions, a concrete user queries their own, and an **unset** user returns `[]` — so `_current_user_id=None` never leaks every profile's sessions. `on_resume` re-enters the gate if the process resumed unset (not All-Users). **Every path that picks a profile goes through `_activate_user(uid)`** (sets the id, clears `_view_all_users`, stores `last_user_id`, loads the settings) — startup restore, the first-run popup's create or pick (`_complete_first_run`, new or adopted), and `_on_user_switch`; an activation that skipped the load left the previous/default values in memory under that profile, which the next flush (e.g. the pre-backup save) then wrote over its stored settings. `_on_user_switch` **refuses while `_session_pipeline_live()`** ("Session in progress", picker snapped back via `_refresh_profile`), including the All-Users view: the running session owns its loaded timer/threshold/sound settings and saves under the profile it started with.
- `DatabaseManager.create_user` raises `UserExistsError(user_id, name)` on duplicate. The first-run popup and Settings → User Profile use the shared `UserPickerForm` widget (`app/ui/widgets/user_picker.py`); the form's "Use existing 'X'" button branch goes through `_on_pick_existing_user(user_id)` in `app_manager` (in Settings the pick switches profile through `_on_user_switch`). The picked profile is activated by id as it is (`_activate_user`: its own headset and mock/real mode); typing an existing name at the gate picks it the same way, so first run never overwrites a profile's settings.

## Android back button

- Android hardware back button (`AppManager._on_keyboard`, bound to `Window.on_keyboard`): consumes key 27 (returns `True`) so Kivy's default exit-on-escape never fires, then routes by precedence — while the user gate is active (`_gate_active`, incl. the pre-popup schedule window), `_handle_gate_back` applies double-press-to-EXIT (never falls through into the app, but a fresh-install user who declines to create a profile can still leave); else an open `Popup`/`ModalView` is left to self-dismiss (handler returns `False`); else an open fullscreen graph overlay closes (via the stored `GraphFullscreen.close` `_restore` closure); else Diary detail → `_on_diary_back`; else any non-`live_session` screen → `_switch_screen("live_session")` (syncs the bottom-nav highlight); else on the Session root, **double-tap within 2 s exits** (`_last_back_time`), the first press showing the in-app `_toast` (the native `_android_toast` — `run_on_ui_thread` + pyjnius `Toast` — is kept for toasts raised while the app is leaving). **A Python `str` must cross pyjnius as `android_jni.java_string(text)`** whenever the Java method is overloaded: pyjnius scores a `str` 10 for both `String` and `char[]` and breaks the tie by sorting signatures (`[C` > `L`), so `Intent.putExtra(EXTRA_TITLE, str)` stored a `char[]` and the SAF save dialog's name came up blank; a `CharSequence` parameter never matches a `str` at all, so `Toast.makeText` raised on every call (the double-back toast never showed). Esc on desktop follows the same chain.

## Errors and diagnostics

- Global crash handler (`app/crash_handler.py`) installs `sys.excepthook`, `threading.excepthook`, and a Kivy `ExceptionManager` handler; all three funnel into a modal dialog that auto-copies a markdown report to the clipboard. Dismiss exits via `app.stop()`. Same module exposes `report_soft_error(label, detail, *, force=False)` for handled-but-significant errors — reuses the dialog with a non-fatal banner and "Close" button (no `app.stop`), and is gated by a 60 s per-label cooldown to prevent spam. Wired to BT connect failures and to the **Copy Diagnostics** button in Settings → Device (which passes `force=True` to bypass the cooldown).
- Perf instrumentation: `app/logger.py` `timed(label)` context manager logs `[PERF] label: N.Nms` when `EEG_PERF=1` (off by default). Wrap a block to benchmark it; on-device it needs a temporary `os.environ["EEG_PERF"] = "1"` at the top of `main.py`, since p4a passes no host environment to the app (`p4a_env_vars.txt` holds only p4a's own vars) — then grep logcat for `[PERF]`. Timing that must always be on stays aggregated instead (see `render_stats` in [eeg-bluetooth.md](eeg-bluetooth.md)).

## Tests

- `tests/test_silent_failure_guardrail.py` is an AST guardrail run on every `pytest` (issue #29 invariant): it scans `app/` and fails on a **silent user-gate return** (`if not self._current_user_id: return/pass` with no user-feedback call) or a **discarded bool-returning DB write** (`add_saved_program`/`add_saved_formula` result ignored). A legitimately-silent site is grandfathered with a standalone `# silent-ok: <reason>` marker (not a ruff noqa code) that must carry a reason. The gate itself is opened by the single `_open_user_gate(delay)` (build / on_resume / self-delete all route through it) and its decision is `resolve_startup_user(db)`.
- `conftest.py` sets `KCFG_GRAPHICS_MAXFPS=0` before Kivy loads: tests pump frames themselves, and the 60 fps cap only slept between them.
  It adds `--run-slow` (tests marked `slow` are skipped without it; the pre-push run passes it) and `_restore_config`, so a test's change to `APP`/`METRICS`/`SIGMOID` doesn't reach the next file.
  `_temp_files_in_basetemp` points `tempfile` at pytest's basetemp, which pytest rotates: an `AudioEngine` removes its sound folder only in `cleanup()`, which many tests never call.
  At import, conftest wraps `noise`'s `_generate_*_wav` synthesizers in `functools.cache` (and fails if the pattern matches none): the app builds one `AudioEngine`, the tests many, and each would synthesize the same sounds again.
  It has to run at import, before the test modules bind the synthesizers by name (`from app.audio_feedback.noise import _generate_bell_wav`).
  It also removes Kivy's Python-2-only `ObservableList`/`ObservableReferenceList.__setslice__`.
  Kivy 2.3.0's Python 3.12 wheel is built with Cython ≤ 3.0.0, which leaks the traceback of every exception caught inside compiled code (fixed in Cython 3.0.3, cython#5724).
  Those methods always raise AttributeError and Kivy calls them on every `pos`/`size` read and change, so over a run the leaked tracebacks grew to millions of objects that every full collection rescanned; without them Kivy takes its `__setitem__` fallback directly.
  The rest of the leak, `WeakProxy.__ref__` raising on dead proxies while Kivy unbinds a dropped widget, stays: removing it would mean copying Kivy's code.
  The app keeps Kivy as it is: it builds its screens once, so its leak stays small.

## Build and CI

**Removing an Android requirement doesn't remove it from local builds.** p4a keeps it installed in `.buildozer/android/platform/build-arm64-v8a/build/python-installs/eegmeditation/arm64-v8a/` and keeps reusing the dist `.buildozer/android/platform/build-arm64-v8a/dists/eegmeditation/` (its `dist_info.json` lists the recipes it was built with — a superset of the current ones still counts as a match), so every later APK keeps bundling it. A numpy probe (2026-10-01) left numpy + Cython (+16 MB) in every build after `numpy` was taken back out of `requirements`. After dropping a requirement, delete that package from `python-installs/` and the `dists/eegmeditation` folder (the next build recreates the dist in about a minute), then check the bundle: site-packages live inside `lib/arm64-v8a/libpybundle.so`, a tar inside the APK. CI builds start clean and are unaffected.

- Windows CI build sets `KIVY_DOC=1` in the PyInstaller spec to prevent GL init on headless runner; Kivy data paths (`kivy_install/data/`, `kivy_install/modules/`) are constructed manually instead of importing `kivy.tools.packaging.pyinstaller_hooks`.
- Linux CI uses system Python (ubuntu-24.04) instead of `actions/setup-python` to get `socket.AF_BLUETOOTH` support.
- MDI icon font path resolution tries multiple candidates for cross-platform compat (standard, Android, fallback).

- **Java sources** live in `android_src/` (a Gradle source root, `android.add_src`); a service there is declared with `--native-service=<class>` in `p4a.extra_args`, which p4a's manifest template writes without `android:process`. That template line has no `foregroundServiceType`, which targeting API 34+ requires (#23): that needs a newer p4a or a template override.

## Background running (Android)

- **A maker's power manager can close the app at foreground-service priority.** Huawei's PowerGenie (EMUI 9+) force-stops the whole package during a locked session with the process at adj 200, the foreground-service level: `am_kill … 200, stop org.eeg.eegmeditation from pid … iAwareF[PowerGenie]` in the events buffer. It did so under the separate-process keep-alive and under the in-process service alike ([session](session.md#screen-lock-and-android)), and not in every locked session. PowerGenie's rules aren't published: it kills apps outside a built-in whitelist, and no API adds one (dontkillmyapp.com). The user-side lever is Battery › App launch › Manage manually.
- **`PowerExemption`** (`app/ui/power_exemption.py`, the app's `_power`) does what the app can: it reads Android's battery optimisation (`PowerManager.isIgnoringBatteryOptimizations`) and the maker (`Build.MANUFACTURER`). A maker's own setting has no API, so for `AGGRESSIVE_MAKERS` (dontkillmyapp's 3-of-5 or worse) it can only explain and open a screen. `offer_once` shows the alert at the first start with something to allow, after the profile gate (from `on_start`, or from `_finish_first_run` on a first run), and records `power_alert_shown` app-wide: it is the phone's setting. A phone with nothing to allow isn't marked, so a lost exemption still gets the alert. `refresh` keeps Settings → Device's row (`DeviceSection.show_power_state`, attached only when Android answers) current at every start and resume, since the user may change it in the phone's settings.
- **Screens it opens**, the first that opens, on Android's UI thread; none (or a JNI failure building them) → a toast. There is no `resolveActivity` check: from Android 11, at target 33, it can't see other apps' screens without a `<queries>` entry and would skip one that is there. Battery: `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, Android's own dialog, which needs the `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` permission; Google Play allows it only for some kinds of app, and without the permission the dialog closes at once with no error, so the list after it (`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`, the fallback where the dialog isn't on the phone) is never reached: a Play build (#23) must open the list instead of the dialog. Huawei and Honor: App launch, `com.huawei.systemmanager/…startupmgr.ui.StartupNormalAppListActivity`, then the older `…appcontrol.activity.StartupAppControlActivity`; EMUI 12 refuses both to other apps (they need `com.huawei.permission.external_app_settings.USE_COMPONENT`, `signature|privileged`), so then the Battery screen (`POWER_USAGE_SUMMARY`, Huawei's `HwPowerManagerActivity`), where App launch is one tap away, and the advice names that path. App info (`ACTION_APPLICATION_DETAILS_SETTINGS`) comes last, and it is the only screen for the other makers: on EMUI 12 it has no battery or launch setting at all. On EMUI 12 `isIgnoringBatteryOptimizations` can answer true while `dumpsys deviceidle` lists no user app, so on Huawei the Battery line can be missing though nothing was allowed. Honor phones on MagicOS moved it to `com.hihonor.systemmanager`, with no confirmed screen name: they get the Battery screen, or App info.

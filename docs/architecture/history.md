# History

The History screen: calendar/14-day chart, totals, the RecycleView session list, select mode. Hard rules are summarized under **Invariants** in [CLAUDE.md](../../CLAUDE.md); this file holds how the subsystem works and why.

## History screen

- **History screen** (`history_screen.py`): Calendar/14-Day segmented toggle at top — `CalendarHeatmap` (GitHub-style, by avg shamatha) or `Last14DaysBars` (per-day bar chart). **Totals table** (#58): Day / Week / Month rows around the filtered day, or today (`_today()`) when none, then an All time row (`period_totals.ALL_TIME`, `date.min`–`date.max`, the same whichever day is shown) — columns Total, On target, Best streak. `app/ui/period_totals.py` is the pure model: `periods_around(day, today)` gives `(label, first day, last day)` for the day, its Monday–Sunday week (the calendar's) and its month, labelled ("Wed 7 Oct", "28 Sep – 4 Oct", "October", or "October 2025" for another year than today's); `period_totals(sessions, start, end)` sums `duration` and `time_above_threshold` ("on target": each session against its own target — a program's segments and a moved threshold included, recorded since #83) and takes the max `longest_streak` (a streak doesn't span sessions) over the sessions whose day falls in the range — `session_day(session)` (`date_time[:10]`, compared as strings: ISO dates order as strings do, no parsing), which the calendar's day buckets and the day filter use too; no query — History's own session list. Sessions from before #51 measured their time above on Meditation; the sum takes each as stored. The table is built once (`_build_totals`) and refilled by `_update_totals` from `_set_day_data` (load, delete), `_set_filter` (tap, Show all) and `on_pre_enter` (also called from `_refresh_ui_after_resume` when History is the current screen), which re-runs `_set_day_data` only when `_today()` differs from the day it last drew for (`_drawn_for`): the calendar, the bars and the totals all take "today" from `_today()`, and an entry on the same day redraws nothing; a period without sessions shows "–". `_place_totals`, bound to the page's width, puts it under the chart, or beside it (between the chart and the Cal / 14d buttons, `_TOTALS_BESIDE_W` = 290 dp, its widest texts) once the page fits the heatmap at its smallest cells next to it (`_TOTALS_BESIDE_FROM`, derived from the heatmap's margins, weeks and minimum cell: ~670 dp): on a landscape phone (~730 dp) the full-width heatmap is ~230 dp tall, so under it the list had no room; beside it the narrower heatmap is ~170 dp. A narrower landscape window keeps it under the chart, where the heatmap would otherwise draw beneath the table. The chart row and the table (when under it) live in one `_chart_area` (vertical, `minimum_height` → `height`); the chevron right after the title, which takes its text's width (`_btn_collapse`, a `theme.FoldChevron` — the one fold button, also the session detail's: the accordion's chevrons, down open and right folded, swapped by `show_folded` through `StyledButton.set_icon`; "Hide"/"Show" text without the icon font; 40 dp, as an icon-only `StyledButton` narrower than ~36 dp crops its glyph to a tick) folds it away by **detaching** `_chart_area` from the page (`set_chart_collapsed`; `chart_collapsed` is "has no parent") and re-inserts it under `_title_row`, so the list takes the room — never hidden in place (a disabled or zero-height widget still takes taps). The tapped day and the totals are untouched by folding. The state is a per-user registry setting, `history_chart_collapsed` (getter/setter on the screen; the chevron's callback persists it); the "list settled" log line carries `chart_h` (the chart row), `chart_w` (the calendar's width: Kivy's default 100, or 0, while the 14-day bars are shown, since the calendar is then detached) and `page_h`. A chart row of 132 dp on the phone is the bars' fixed height; the calendar's is width-derived (~150 dp upright). Kivy's scroll effect rounds a resting position to a whole pixel, so with a list of fractional height its top is within a pixel of `effect_y.max`, not on it. Both share `set_data(day_values)` + `set_day_tap_callback` so tap-to-filter works in both modes. Selected mode persisted as per-user setting `history_view_mode`. Day filter, session list with inline rename/delete unchanged. **Multi-select CSV export** (issue #7): a **Select** button enters select mode — `set_select_mode(on)` re-syncs the rows on screen so each gains a leading checkbox and drops its rename/delete (attached and detached, not hidden in place, which keeps the touch layer clean; no row is rebuilt — see the History list below); the `_list_touch_down` router toggles a row's selection on tap in select mode, and Select all selects every session in the current filter, including rows never shown. A `RevealBox` action bar (Export N / Delete N / Select all / Cancel) is revealed only in select mode (detached otherwise). **Delete N** (#57) → `delete_selected()` → `_confirm_delete(ids)`, the one confirm for a row's delete and the selection (one session: its `session_title`; several: the count, the days and, when they span profiles, how many), then `on_delete_sessions(ids, done)`: `done(True)` ends select mode, a failure keeps the selection. The confirm is the shared `theme.confirm_popup` (a second, hand-built one let a Delete tapped during the fade after Cancel delete the selection). A selection survives a day-filter change, as Export's does: the count on the button and the confirm's day span show what goes. `_selected_ids` + `toggle_session_selection`/`select_all_shown`/`export_selected` are the model (unit-tested); `export_selected` calls the `on_export_sessions` callback with sorted ids → `AppManager._on_export_sessions_csv`, which loops `export_session_csv` off-thread, `csv_export.build_sessions_zip(path, {sid: csv})` (one `session_<id>.csv` entry each, skips empty), and delivers via the shared `android_share.copy_to_documents` (works on desktop + Android).
- `history_view_mode` per-user setting (`"calendar"` | `"bars"`, default `"calendar"`) selects the History layout via `HistoryScreen.set_view_mode(mode)`. Both `CalendarHeatmap` and `Last14DaysBars` consume the same `day_avg` dict and share the tap-to-filter callback.
- **The chart's period** (#44). Both charts are `_DayChart`s that `_draw` `window(end)` for the one period end `HistoryScreen` owns, read through `set_period_source`: `period_end` is today plus `_period_offset` days (0 for today's page, negative for an earlier one). Kept as an offset, a page stays as many days back as the day moves on, still meeting today's, with no bookkeeping at midnight. A chart off screen doesn't draw (`_redraw` is a no-op while detached); `set_view_mode` draws the one it shows. It has to: upright on a narrow phone the calendar keeps its smallest cells, as tall as the bars, so a chart shown again lands where it was and no size or position change redraws it.
  - **Windows:** `Last14DaysBars.window(end)` is the 14 days ending at `end`. `CalendarHeatmap.window(end)` is `WEEKS_VISIBLE` (18) whole weeks from a Monday, the last one `end`'s, but never past today: drawing only up to `end` would leave each page's last-week days after `end` on no page, since a page steps 18 weeks.
  - **Paging:** `shift_period(direction)` steps the shown view's `step(end, ±1)` (14 days or 18 weeks). Forward stops at today (an offset at or past 0 becomes 0); back stops once the window holds the first session (`_first_day`, from the day buckets).
  - **Controls:** ‹ and › (`C.PRIMARY` glyphs on the card, so a disabled one greys) around the period's dates (`period_text`: `period_totals.day_range`, the totals' week format, plus the year wherever it isn't this one); a tap on the dates goes back to today. `_place_totals` places the row with the table: upright, over the chart inside `_graph_wrap`, so `_graph_row` is the chart's height plus `_PERIOD_H` (`_fit_graph_row`); sideways, over the table in `_side_col` beside the chart, which is taller than both, so the list loses nothing. Switching views keeps the period end; another profile or the All Users view (`load_sessions(keep_filter=False)`) starts at today, like the day filter.
  - **Touches:** `_DayChart` grabs a touch on the chart, a wheel tick excepted, and decides on the lift. A sideways move of at least `_SWIPE` (40 dp), more sideways than vertical, pages (right brings earlier days in); one within `_TAP_SLOP` (20 dp) is a tap on the day under where the finger came down; anything between does nothing, so a swipe that starts on a day picks none. The day filter doesn't follow the period: a picked day stays picked on any page, named by the date label over the list.

## Session list

- **The History list is a RecycleView** (#42): `_SessionList` (`_StableScrollView` + `RecycleView`) holds one data item per shown session (`_item(session)`: sid, the `session_labels` title, stats line and notes line, score colour, `card_h`, `height`) and builds `_SessionRow` widgets only for the rows on screen, reused while scrolling. One widget tree per session was the cost: 16 widgets each, all rebuilt on every load, day filter, Show all and Select/Cancel — on the phone with a few hundred sessions a load took 14–22 s behind a full-screen spinner and a Select or Cancel 14–20 s, and slower per row as the list grew (each appended row moved every row above it; every garbage collection scanned ~6,300 more objects per row). Desktop with the Android build's Kivy 2.3.0 / Python 3.11 (2026-10-02, mock sessions): 250 sessions 2.7 s → ~60 ms first paint, 1000 sessions 20.7 s → the same; a reload rebinds the existing rows (~30–60 ms). There is no spinner (`_refresh_history` no longer calls `show_loading`). State a row shows but the session doesn't own — `_select_mode`, `_selected_ids`, `_renaming_sid` — lives on the screen, and `_SessionRow.sync(owner)` applies it from `refresh_view_attrs` **and** `on_parent`: Kivy reuses a row that returns to the index it last showed *without* calling `refresh_view_attrs`, so it kept the checkbox or editor of a change made while it was off screen. `_sync_rows()` re-syncs the visible rows after a select-mode or selection change (no data change, no new widgets). Every list operation is a data update: `_show_sessions` (a new list, from the top), `remove_sessions(ids)` (drops the items and the model entries — `_sessions`, `_shown`, `_selected_ids` — refreshes the header count and the calendar/bars `day_avg` via `_set_day_data()`, keeps the scroll position and any day filter), `_update_item(sid)` (one item's name and height after a rename opens, closes or saves). Inline rename is one editor (`_rename_row`, a `theme.RenameRow`, with its `_rename_input`) attached to the row showing `_renaming_sid`, whose item is `_RENAME_H` taller; a row scrolled off screen detaches it and drops its focus (`on_parent(None)`), so the editor follows its session with the typed text. The pencil focuses it a frame later (`RenameRow.focus_soon`, only if it is still shown): Kivy unfocuses every input a tap didn't land on after that tap's touch-up, so focusing it in the tap left no keyboard. `load_sessions` keeps only selected ids that are in the new list (another profile's selection was exported with the next profile's). Row height comes from the data, not from measured widgets: `_ROW_H` (two lines) or `_ROW_H_NOTES` (three, when the session has notes; the notes label is detached, not emptied, on a two-line row), plus `_RENAME_H` while the editor is open; every row label is one line, cut with an ellipsis (`shorten`). A delete used to rebuild every row (measured on the phone with a few hundred sessions: 12 ms DB delete, then a 22 s full-screen spinner, landing at the top) and also rebuilt the hidden diary list. **The blank list (rows built, none visible, until restart, #56) was Kivy's ScrollView rescaling an overscroll**: on every content-height change `_update_effect_y_bounds` re-derives the effect's pixel position as `max * scroll_y`, and past an edge `scroll_y` is outside [0, 1] — so while the list was overscrolled (a fling past the end) and row chunks kept arriving, the overscroll in pixels grew with the list, the damped-scroll spring pumped it further and the view ran off the content. The list's content height is now set from the data at once, but it still changes under the user (a delete, the select bar showing), so `_StableScrollView._update_effect_y_bounds` keeps the **pixel offset from the top** when the content height really changes (no overscroll growth, no rounding drift, nothing sliding under the finger) and defers to Kivy when the bounds are unchanged — Kivy calls it on every touch start/stop, so a clamp there killed the normal edge bounce. A new list starts with `effect_y.reset(effect_y.max)` (top, velocity and overscroll 0 — setting only `scroll_y` was overwritten by a fling still in flight): scroll programmatically through the effect (`effect_y.reset(effect_y.max * y)`), since an assigned `scroll_y` leaves the effect's value behind and its next update moves the list back. Any other ScrollView whose content changes while the user may be scrolling needs the same override. The day filter has one owner, `_set_filter(date | None)` (the filtered day, both the calendar's and the bars' highlight, the Show-all button); a reload of the same profile/view keeps it (`load_sessions(..., keep_filter=)`, decided by `AppManager._history_view`), another profile or the All-Users view clears it, `_show_sessions` sets `_shown` even for an empty list (then `_empty_label` shows; a stale list let Select show and export the previous profile's sessions), `_activate_user` and `_on_user_delete` mark History dirty. `_log_list_state` logs the session count, the row widgets, list/viewport height and the scroll effect's value/bounds/velocity 1 s after a new list (`settled`, cancelled by the next list).

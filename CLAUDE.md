# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

EEG Meditation Trainer — a Python/Kivy application for Shamatha meditation training using EEG neurofeedback from NeuroSky MindWave Mobile 2. Targets Android (via Buildozer), Linux, macOS and Windows (via PyInstaller) desktops.

## Commands

```bash
# Run application
python main.py

# Run with serial device (e.g. from mindwave-splitter)
python main.py --serial /tmp/mindwave_b

# Run all tests
python -m pytest tests/ -v

# Run a single test file
python -m pytest tests/test_engine.py -v

# Run a single test
python -m pytest tests/test_engine.py::TestMetricsEngine::test_compute_metrics -v

# Build Linux executable
./build_linux.sh              # output: dist/EEG_Meditation_Trainer/

# Build Android APK
./build_android.sh            # debug build
./build_android.sh release    # release build

# Build Windows executable (run on Windows)
build_windows.bat

# CI: build a single platform via workflow dispatch
gh workflow run release.yml -f platform=windows   # or linux, macos, android, all
```

**Removing an Android requirement doesn't remove it from local builds.** p4a keeps it installed in `.buildozer/android/platform/build-arm64-v8a/build/python-installs/eegmeditation/arm64-v8a/` and keeps reusing the dist `.buildozer/android/platform/build-arm64-v8a/dists/eegmeditation/` (its `dist_info.json` lists the recipes it was built with — a superset of the current ones still counts as a match), so every later APK keeps bundling it. A numpy probe (2026-10-01) left numpy + Cython (+16 MB) in every build after `numpy` was taken back out of `requirements`. After dropping a requirement, delete that package from `python-installs/` and the `dists/eegmeditation` folder (the next build recreates the dist in about a minute), then check the bundle: site-packages live inside `lib/arm64-v8a/libpybundle.so`, a tar inside the APK. CI builds start clean and are unaffected.

## Architecture

**Entry point:** `main.py` → instantiates `EEGMeditationApp` (Kivy app with ScreenManager).

**Data flow:** EEG stream → MetricsEngine → SessionManager → UI screens + Database

### Core modules

- **EEG sources** (`app/eeg/`): `mock_stream_v2.py` (active mock with frequency-based synthesis, NeuroSky-compatible format), `mock_stream.py` (legacy mock), and `neurosky_stream.py` (real Bluetooth RFCOMM / pyserial, ThinkGear protocol). Both active sources produce 8 band powers + raw 512Hz waveform + eSense attention/meditation. Desktop BT falls back to PyBluez if `socket.AF_BLUETOOTH` is missing (common in PyInstaller bundles). Real stream tracks `_last_packet_time` for stale data detection and parses battery level (code 0x01, though TGAM hardware doesn't send it). BT connection kept alive between sessions to avoid RFCOMM/EBUSY issues; `reset_sample_state()` clears cached values for new sessions.
- **Metrics pipeline** (`app/metrics/engine.py`): Consumes raw band powers, computes meditation score, shamatha score, distraction, sinking, subtle distraction. **Distraction & sinking are ported from the original Vernihor app** (`reference_distraction`/`reference_sinking`), not sigmoids: both are gated to 0 by alpha dominance and modulated by `(140 − S')` where `S'` is shamatha *before* the final −20 offset and clamp (exposed via `MetricsEngine.last_s_prime`); distraction is the raw `100·(β1+β2)/α1` ratio, sinking is `(45 − a2p)/0.26` then gamma-damped. Their gates use `sqrt_pct_8band` — `round(sqrt(raw/P8)·100)`, an 8-band sqrt-relative percent (0–100), distinct from the 6-band `compute_sqrt_relative_bands` the shamatha formula uses. Subtle distraction still uses sigmoid normalization of short-window variance. Each saved session is stamped with `MetricsEngine.ENGINE_VERSION` (`sessions.engine_version`, "2" = ported formulas; "" = pre-versioning sigmoid era) so stored values stay attributable — the diary reads stored distraction/sinking, it does not recompute them, so old sessions render unchanged. Uses rolling buffers from `app/eeg/buffer.py`. Power-line noise detection in `app/metrics/noise_detector.py`.
- **Custom formula engine** (`app/metrics/custom_formula.py`): AST-parsed user-defined expressions with whitelisted functions and `avg(expr, N)` windowed averages.
- **Session lifecycle** (`app/session/manager.py`): Start/Pause/Resume/Stop state machine. Coordinates EEG stream, metrics engine, audio feedback, and database flush. Tracks `time_shamatha_90` (time shamatha score >= 90, independent of user threshold).
- **Session program** (`app/session/session_program.py`): headless model for ordered timed segments — see Key Design Decisions.
- **Audio feedback** (`app/audio_feedback/noise.py`): 4-channel engine — selectable continuous feedback (log-scaled volume, MAX_VOLUME=0.3), tingsha bell (sinking), chime (subtle distraction), warble (disconnect alert). Uses Kivy SoundLoader with crossfaded WAV generation. On Android, the feedback channel and the **timer-end gong** use `MediaPlayer` (with `USAGE_MEDIA` audio attributes) instead of SDL_mixer so they keep playing through screen lock; SoundLoader/SDL is silenced while locked. The other one-shot channels (sinking bell, chime, warble) still use Kivy's `SoundLoader`. `AudioEngine.mute()` is a non-blocking volume→0 (setVolume only) safe to call from the tick thread during lock. **Selectable feedback source** (issue #10): `AudioEngine.prepare_feedback(sources, active_id)` (main-thread) pre-instantiates one looping player per distinct source id (`"noise"`, `"tone"`, `"heartbeat"`, or a custom file path); `set_active_feedback(source_id)` is setVolume-only — the active player goes to the modulated volume, all others go to 0. No player is created or released mid-session; switching is tick-/lock-safe under the same deadlock-avoidance rule as `mute()`. **Pause keeps the player set** (#37): `_on_pause` calls `AudioEngine.pause()` (volume 0 + `player.stop()` on every prepared player, ramp stopped, `_is_playing=False` so the bell/chime alert gates and `update()` go quiet) and `resume()` (replays the same players through `_play_prepared`, the ramp restores each role's last target) — never `stop()`/`start()`, because `stop()` tears the prepared set down and only `_start_session_common`'s `prepare_feedback` + `set_reward` rebuild it, so Resume used to leave both channels silent for the rest of the session (with the alerts still firing, which read as "the sound changed"). `stop()` remains the real session-end teardown. The `"tone"` source generates a harmonic-pad drone (fundamental + fifth) lazily at session start. The `"heartbeat"` source (issue #11 — stable internal id; the timbre is **Crickets**) generates a looping `_NOISE_BUFFER_SECONDS`-long WAV that is a silent bed with one `_HEARTBEAT_PULSE_SECONDS` (0.1s) cricket chirp — a high tonal carrier (~4.8kHz) + 2nd harmonic gated by a ~40Hz half-wave amplitude trill, Hann-windowed to zero at both ends (`_generate_heartbeat_wav`, cached at `_heartbeat_path`) — so a periodic ~10s chirp rides the same continuous looping player + volume ramp with **no** tick-loop scheduling; loop edges stay silent → gapless. It's **reward-only** (offered in the reward picker as "Crickets", not the below-feedback picker). `test_audio(reward_id)` previews the reward source first (players are near loop start so the chirp is caught) before the below-channel sweep; `_on_test_audio`/`_test_audio_sources` prepare both the below and reward sources. `EEGMeditationApp._feedback_plan` / `_source_spec` / `_feedback_source_id` / `_global_feedback_id` resolve the global setting and per-segment override (`""` inherits global); `_apply_program_segment` calls `set_active_feedback` at each boundary. Persisted per-user: `feedback_source` (`"noise"` / `"tone"` / `"custom"`) and `feedback_sound_path`. **Dual-zone feedback** (issues #12, #9): two metric-keyed channels driven from one `update(score)`. The **below** channel is the existing noise (`compute_volume`: log curve, 0 at/above threshold). The **above-threshold reward** channel (`compute_reward_volume`: mirror log curve rising 0→max over `[threshold, threshold + APP.REWARD_SPAN(=30)]`, clamped) is a second prepared player designated by `set_reward(source_id)` (`""`=none). Both zones are 0 exactly at the threshold → clean cross-fade. The ramp loop now drives **every** prepared player toward its role target (below→`_target_volume`, reward→`_reward_target_volume`, others→0); volume-only, tick/lock-safe. A channel source of `"none"`/`""` (`_source_spec`→`("none","")`) instantiates no player; `prepare_feedback` skips `kind=="none"`, and `_resolve_active("" | "none")` returns `""` so a None **below** channel never grabs the reward player. `_teardown_feedback_players`/`stop` reset `_reward_feedback`, so `set_reward` must be called **after** `prepare_feedback` at session start (the order `_start_session_common` uses). Reward is **global only** — programs keep per-segment switching on the below channel; reward stays armed across segments. `EEGMeditationApp._reward_id()` resolves the reward source (custom-missing → silent, unlike noise→rain). Persisted per-user: `reward_source` (`"none"`/`"noise"`/`"tone"`/`"heartbeat"`/`"custom"`, default `"none"`) + `reward_sound_path`; `_on_reward_source_change` mirrors `_on_feedback_source_change`. Subsumes #9. **Source selection UI**: both the feedback and reward sources are chosen through a shared **popup picker** (`SettingsScreen._open_source_picker(title, options, on_choose)` → `_choose_feedback_source`/`_choose_reward_source` → `_apply_*_source`), not a button row — one picker button per channel showing the current label (`_source_label`); `"custom"` opens the file chooser directly (no separate custom-path row / RevealBox). `_FEEDBACK_SOURCE_OPTIONS` omits Crickets; `_REWARD_SOURCE_OPTIONS` includes it.
- **Storage** (`app/storage/database.py`): SQLite with automatic schema migration. Stores sessions (with `session_name`, `time_shamatha_90`, and `score_metric_key`/`score_metric_name`/`avg_score` — the metric the session was scored on, #51 — columns), per-tick metrics timeseries, user profiles, per-user settings. CSV export support. `create_user` raises `UserExistsError` on duplicate name; `find_user_by_name` looks up by exact (case-sensitive) name. Per-user settings are a flat KV store (`set_user_setting`/`get_user_setting`, key = `user_{id}_{key}`); `set_user_json_setting`/`get_user_json_setting` wrap a value as JSON in one key (the pattern used by `saved_formulas`, and by per-graph series / active-formula lists). The connection is accessed through a single self-healing `_conn` **property** (backing `_conn_obj`) so no read/write path can deref a `None` connection: if the conn was closed while the app is still running it reopens the DB file (lock-guarded reconnect); once `mark_shutting_down()` is set it returns a **null connection** (`_NULL_CONN`) that swallows writes and returns no rows, so late access from any path (reads, writes, the daemon tick thread) is a **benign no-op** — never a crash, never a reopen that resurrects a closed process or clobbers a freshly-restored DB. `on_stop` and `_do_restore_and_restart` both `mark_shutting_down()` before `close()`; `on_pause` also skips the settings flush while `_restoring`. So editing settings never silently vanishes, teardown never crashes, and a restore is never clobbered. `delete_user` **purges** the user's sessions, metrics, and `user_{id}_*` settings in order (FKs are declared but not enforced — no `PRAGMA foreign_keys`/cascade — so an explicit ordered delete is required; uses GLOB not LIKE so the literal `_` in the key prefix isn't a wildcard). Without it, deleting a profile orphaned its sessions (which then surfaced in the All-Users view), metrics, and settings rows forever. The confirm (`SettingsScreen._confirm_user_delete`) therefore states the profile's session count and that they are deleted with it — it used to say only "All their settings will be lost."
- **DB backup/restore** (`app/storage/backup.py`): `online_backup_to_tempfile` (SQLite online `Connection.backup()` into an internal temp file), `make_backup` (temp + `copy_file_atomic`, desktop), `validate_backup` (checks for required tables), `restore_backup` (validates, `copy_file_atomic`, then removes the replaced DB's `-wal`/`-shm` so SQLite can't replay them onto the restored file). **Every app file copy goes through `app/storage/fileops.copy_file_atomic(src, dst)`** — bytes only, into a temp file beside `dst`, fsync, `os.replace` (so `dst` is untouched or complete) — never `shutil.copy2`: in Android app storage copying the SELinux label raises EACCES, which the phone's Python 3.11 `shutil` doesn't ignore (3.12 does), *after* the data is written, so Restore replaced the DB and then reported `restore_failed` and skipped the relaunch (#63). The same EACCES is the harmless Kivy `Error when copying logo directory` on the first launch after an install. `discard_file(path)` is the shared remove-and-log for temp/leftover files. Android backup/restore go through the Storage Access Framework (`app/storage/android_saf.py`) since scoped storage blocks direct `/sdcard` access. Used by Settings → Data Backup section.

The ring is a `Line` drawn in `_redraw` at `_ring_rgb()` = `C.TEXT` — contrast derives from the **surrounding surface** (light on dark themes, dark on light), NOT the button fill, same rule as the graph expand glyph; `readable_fg(fill)` would give a dark ring on a bright accent button that then vanishes on a dark theme. `flash_confirm(text="Saved", icon=None, confirm_color=None, duration=1.1)` is the action-confirmation cue (issue #33 E): it morphs the label (and optionally the icon / fill) to a success state, then `Clock`-reverts to the **true** original (reentrancy-safe — a repeat tap restarts the timer without capturing the intermediate state). Main-thread only. **Configuration:** All tunable parameters (sigmoid curves, thresholds, update frequency, audio settings) are in `app/config.py` as dataclass-style config objects (`SIGMOID`, `METRICS`, `APP`).

### Diagnostic tools (`tools/`)

- `bt_test.py` — Minimal raw RFCOMM + ThinkGear parser for connection debugging. No Kivy, no threads. Usage: `python tools/bt_test.py [MAC] [seconds]` (default 30 s). Prints only the ~1 Hz packets (printing all 512 raw-wave packets/s stalls the reader and fakes dropouts) and ends with the single-byte codes the device actually sent (e.g. whether battery 0x01 ever appears).
- `ble_battery_scan.py` — BLE GATT service enumerator (requires `bleak`). MindWave Mobile 2 doesn't expose BLE on Linux/Android (iOS only).

## Key Design Decisions

- Update loop runs at 2Hz (`AppConfig.UPDATE_FREQUENCY = 0.5s`), graph holds 600 points (5 min).
- Band powers are sqrt-normalized to relative units before metric formulas.
- NeuroSky Bluetooth uses pyjnius on Android, Python socket BTPROTO_RFCOMM on Linux (with PyBluez fallback), pyserial over virtual COM port on Windows. BT connection is kept alive between sessions (not closed on session stop) to avoid RFCOMM EBUSY and ThinkGear reinit failures. On app exit, the socket is NOT explicitly closed — the kernel handles cleanup while BlueZ may keep the ACL link for faster next-launch reconnect. Connection timeout is 30s, signal wait is 8s. Stale data (no new packets for 10s) auto-stops the session.
- **The MindWave serves one RFCOMM channel — a connected socket nobody drains stalls its transmitter until the headset is power-cycled**, so `NeuroSkyStream`'s reader lifecycle must never orphan one, and **at most one reader thread may exist**. That single-reader invariant is the real guarantee: readers share `_bt_socket`/`_running`/`_connected`, so with two alive a late reader's `_adopt_socket` overwrites the live one's socket reference and its failure path kills the live session — the epoch check cannot prevent that. `start()` bumps `_connect_epoch`, passes it to `_read_loop(epoch)` and **returns a bool**: False (with `_last_connect_error` set) when refused — no device, or a previous reader still alive ("Previous connection is still closing"). `stop()` sets `_stop_event`, bumps the epoch, and closes the socket **before** `join(_STOP_JOIN_TIMEOUT=5s)`; the close interrupts **every** blocking point: Android `connect()` (`_run_connect_attempts` publishes each socket as `_pending_socket` before `connect()` and re-checks `_running` after publishing, so `stop()` either closes it or the reader sees the stop; `BluetoothSocket.close()` from another thread aborts `connect()`), Android read (socket close), desktop `connect()`/`recv()` (`_shutdown_before_close` → `shutdown(SHUT_RDWR)` on native and PyBluez sockets — on Linux a cross-thread `close()` alone doesn't wake them), serial read (`select` 0.5 s poll — a cross-thread `os.close()` doesn't wake `os.read()`), and the back-off sleeps (`_stop_event.wait`). An aborted connect raises instead of falling through to the next method, and the superseded reader returns quietly without writing `_last_connect_error`. A headset-off connect chain is ~3×7.7 s on-device, so without the abort `stop()` froze the main thread for the full join. If the join still times out, `stop()` **keeps** `_thread` so `start()` refuses (nulling it let a second reader start); it joins a local copy because the tick thread and the main thread can both be in `stop()`. `_close_socket` runs under `_close_lock` (stop() and the exiting reader both call it). A single late reader (epoch superseded after its connect returned) closes its socket instead of adopting it; `_last_connect_error` is cleared only after that check; and the reader clears `_connected` on exit, so a stop() landing just after `_connected = True` can't leave `is_connected` stuck True with no reader (which made the next Start "reuse" a dead connection). Every failed Android connect attempt (secure → insecure → `createRfcommSocket(1)`) closes its socket; the ch=1 fallback is called directly on the device — the former `Class.getMethod` reflection hit a pyjnius varargs error and never reached Bluetooth. In `app_manager`, `_begin_bt_wait()` checks `start()`'s result **before** entering the wait: a refusal releases the wake lock/keep-alive service and shows an honest retry overlay, with no `bt_connect_failed` soft-error (whose 60 s cooldown would otherwise hide the next real failure). **All five BT-wait exits** (Cancel, Stop, no-data, failed connect, timeout) go through `_abort_bt_wait()`, which stops the tick watcher (and clears `_waiting_for_bt`/`_bt_signal_start`) **before** `_real_stream.stop()`, then releases the wake lock and keep-alive service — the watcher reads `not stream._running` as a failed connect, so the old stream-first Cancel produced a false "Connection failed" dialog, and the failed-connect exit used to leak the wake lock and foreground service. **A session start is one attempt** (#52): `_start_attempt` advances on every Start (`_on_start`) and on every ending — `_undo_session_setup()` advances it, and every ending goes through it — and a callback queued for an attempt does nothing once it has moved on: the device scan's result in `_on_start`, and every main-thread callback of the BT wait, which `_handle_bt_wait` queues through `_on_main_for_wait` (the "connected" UI + audio `_on_session_connected`, the three exits' retry screens, the countdown text). The wait's attempt is `_wait_attempt`, taken on the main thread in `_begin_bt_wait` — not read by the tick thread when it queues, because a Cancel can land while the tick is mid-tick, and its 1 s join can time out (`read_sample` waits for the reader's lock), so the tick may queue after the Cancel has finished. A Cancel during "Scanning for MindWave…" used to start the session anyway; a Cancel or an active-profile delete in the frame the first data arrived left a zombie (noise playing, idle controls, no tick, Restore refused); a wait exit's queued retry screen could undo the next Start. `_on_stop` decides by `SessionManager.state`, not `_waiting_for_bt` (a wait exit clears the flag before its idle UI is shown, so a Stop in that window offered to save a session that never started): RUNNING/PAUSED asks to stop and save, FINISHED (the timer ended it on the tick thread; its teardown is queued) is ignored — cancelling there stopped the kept-alive headset link — and anything else cancels the start (`_cancel_session_start`). Every ending — `_finalize_stop_ui`, a cancelled start, a refused connect and the three tick-thread wait exits (their queued callbacks) — undoes the start's setup through the one `_undo_session_setup()` (program series and state via `_restore_program_series`, the training marker, the shamatha pill, timer and session manager reset, wake lock and keep-alive service; the releases are idempotent): a cancelled program session used to leave `_session_program_active` and the program series snapshot behind, which a later simple session then persisted over the user's series selection. A kept-alive connection's start shows the same `_on_session_connected` as the wait's; the header's start time and the graph's wall-clock axis come from `SessionManager.started_at`, not from when the queued UI ran (after a screen lock, the unlock time). If a Cancel's join times out, the late tick can still start `SessionManager` after the Cancel's reset; only its UI and audio are gated. `_waiting_for_bt`/`_bt_signal_start` are initialized in `__init__` (Cancel before any Start used to raise `AttributeError`). Android reads are one bulk `InputStream.read(buf, 0, n)` per chunk, the buffer sized to the read (pyjnius marshals the whole array both ways, so a reused oversized buffer is slower), replacing ~4000 byte-at-a-time JNI calls/s at the 512 Hz raw rate; the reader thread runs at Android priority −8 (the NeuroSky SDK reader's MAX_PRIORITY). `_log_throughput` logs `BT throughput: N B/s, N B/read, backlog high-water N B` every 30 s. Healthy is ≈4132 B/s (512 raw packets × 8 B + one 36 B eSense packet per second); a high-water that keeps rising means the reader is losing. A flat ~2 KB high-water during a live session (≈0.5 s stalls from ~60 s in) tracks Kivy rendering: it vanished for a whole screen lock while the tick thread and DB kept running (measured 2026-09-26) — the main thread holding the GIL during graph redraws. `app/ui/render_stats.py` measures it: every `ScrollableGraphWidget._redraw` is timed per `graph_id` (the drawing itself is `_draw`) and a per-frame `Clock` callback (started in `on_start`) tracks the longest gap between frames, ignoring gaps over 5 s (a suspended loop); every 30 s — the same cadence as `BT throughput` — a window that had redraws logs `Render: frame gap max N ms | <graph_id> Nx avg N max N ms | …`. Measured 2026-10-01 (11-min live session, headset on, Metrics view): the **live metrics graph** is essentially all of it — redraw avg rises 18 → ~63 ms over the first ~2.5 min and then stays flat (max ~160–180 ms, at 2 Hz ≈ 13% of the main thread), the raw and band graphs measure ~0 ms; frame gap max ~210 ms, and the BT high-water doubled (≈300 → ≈600 B ≈ 145 ms of data at 4132 B/s) in the same window the redraw max jumped. So high-water ≈ longest frame gap × throughput: no data loss (throughput steady), but each long redraw is a visible UI hitch, and making `ScrollableGraphWidget._draw` cheaper is the lever (a 2 KB high-water ≈ a 0.5 s frame) — see **Graph drawing cost**. `tests/test_neurosky_lifecycle.py` covers stop-during-connect, refuse-while-alive through the real `stop()`, `start()`'s status, concurrent `stop()`, the stale-`_connected` race, stop waking a blocked desktop `recv` and a silent serial read, connect abort, the successful adopt handover, and failed-attempt cleanup; `tests/test_bt_wait_abort.py` covers the watcher-before-stream order on every exit, the failed-connect wake-lock release, the refused-start path, and `__init__` defining the wait state.

- **Graph drawing cost** (`ScrollableGraphWidget._draw`, rebuilt from scratch on every `add_point` — 2 Hz per live graph — and re-rendered by GL every frame): (1) axis/value labels come from `_LABEL_CACHE` (LRU of 512 `CoreLabel`s keyed by text/size/colour; the `CoreLabel` is kept, not just its texture, because it is the texture's reload observer after an Android GL context loss) — a redraw used to render ~70 fresh text textures; (2) the X grid step is `_x_grid_step(graph_w, visible_seconds)`, the smallest of 10 s … 2 h that keeps time labels ≥70 dp apart (fixed 10 s drew ~160 overlapping labels at a 26-min zoom; default zooms keep 10 s); (3) a heatmap series (`set_heatmap_color`, the live shamatha line) is **one `Mesh`**: a quad per segment plus a square patch per vertex (Kivy `Line.width` is the half-thickness, so the patch half-size is `dp(line_width)`), each vertex's texture v = its height in the 1×64 blue→red `_heatmap_texture()` (clamp-to-edge, refilled by a reload observer), split at `_MESH_MAX_QUADS` = 65535 // 6 = 10922 quads, because Kivy caps a Mesh at 65535 *indices* (GLES2, enforced on Android; 6 per quad) — the first limit counted vertices (16000 quads), so zooming out over ~45+ min of a live session (>5461 visible points) raised `GraphicException` and crashed the app — it was a `Color`+`Line` per segment (~600 instructions per redraw and ~600 draw calls per frame). A stencil mask over a gradient was tried and rejected: Kivy counts overlapping mask fragments (wide-line joints), so `equal` leaves holes and `lequal` leaks outside an enclosing ScrollView's stencil — and `StencilUse(func_op=...)` in the constructor is silently ignored (only the property setter applies; the getter raises on Python 3); (4) `set_drawing_enabled(False)` pauses a graph its owner detached — `LiveSessionScreen._set_view` does it for the hidden Metrics/Raw view (a detached graph keeps its size, so after one visit to Raw the hidden ~5000-point raw graph redrew every tick at ~130 ms); data keeps accruing and the graph redraws once re-enabled. Measured on the phone 2026-10-01 (live metrics, ~26-min zoom): redraw max 160–200 → 38–48 ms and frame gap max 205–250 → 66–72 ms over the first ~5 min. (5) a zoomed-out redraw draws at most 4 points per pixel column (#70): `_fold_columns(values, stops)` keeps each pixel column's first, last, min and max sample (M4 aggregation, Jugel et al., VLDB 2014), in sample order — the line enters and leaves each column at its real samples and spans its real extremes, so it rasterizes like the full series (within 1 px: a thick stroke's half-width reaches the next column) and no peak or dip is lost. The columns are the viewport's pixel columns, computed once per redraw for all series by `_column_bounds(n, offset, per_px)` (a sample's column is `floor((offset + i) / per_px)`, the boundary estimate corrected by that same rule against float rounding), so the folded line moves exactly as the full one would; value labels, markers, the threshold and the time axis keep using the real indices. Folding starts where it is cheaper than drawing every point, which depends on what a point costs: `_FOLD_MIN_PER_PX_HEATMAP` = 4 samples per pixel for the heatmap line (two quads, a patch and texture coordinates per point), `_FOLD_MIN_PER_PX_LINE` = 8 for a plain line (desktop, 2026-10-02: a line at 4/px was 0.9 ms unfolded vs 1.2 folded, at 8/px 1.9 vs 1.4). Only C built-ins touch every sample (`min`/`max`/`list.index` on per-column slices). Desktop (2026-10-02): the live metrics graph with six series at a 3 h zoom 87 → 12 ms (Shamatha alone 39 → 4.4), the raw EEG graph zoomed out to its 60 s buffer 8.1 → 2.1 ms; the 5-minute view and the raw graph at its default 10 s (5 samples per pixel, cheaper unfolded) are unchanged. On the phone (2026-10-02, the same two steps before and after): the live Raw EEG view, zoomed out over most of its 60 s buffer (the live graphs' zoom is linked and saved), went from 48–89 ms average per 30 s window (max 175 ms) to 6–34 ms (max 49 ms) at 2 Hz — still growing with the buffer, since `min`/`max`/`list.index` touch every visible sample in C — and a long session's detail graph zoomed out from 52–68 ms max to ~19 ms (one 42 ms window). The unfolded path also got cheaper (the auto-scale copies each series once and takes its peak in C): desktop band graph, 8 series × 600 points, 1.46 → 1.16 ms. - **A session reaches the DB only through checkpoints** (#30): `_checkpoint_session(stats=None)` → `DatabaseManager.checkpoint_session(sid, stats, ticks, …)` inserts or updates the session row **and** inserts the buffered tick rows in one transaction (`_insert_session` / `_update_session_row` / `_insert_metrics`, the same SQL `save_session` / `update_session` / `save_metrics_batch` use), so a process killed at any point leaves the row and the data of one checkpoint, which agree. It runs at every snapshot point: the 60 s tick flush (`_flush_tick`), the final save (`_persist_session_data`, with the stop's stats), `_flush_on_leave` (on_pause / on_stop, while a session is running or paused) and both backup workers. The row used to be written once, at the first 60 s flush, and only rewritten at a normal stop — a session the app died in (a crash, an Android kill of the backgrounded app) kept ~1 min of stats over all of its data (reproduced: SIGKILL 150 s in → row 59 s, data 120 s; now 119 s / 120 s). A closed window was already saved whole: `on_stop` stops and saves a running session. `SessionManager.elapsed_seconds` is frozen at the pause while PAUSED (it returned the stop-time `_elapsed`, 0, so a checkpoint of a paused session wrote duration 0). Ticks since the last checkpoint (≤ 60 s) are still lost on a kill. `_record_tick` (the tick's `add_metric` + buffer append) and a checkpoint's snapshot of both run under the class-level `_checkpoint_lock`, so a checkpoint from the main or backup thread neither loses a tick nor writes stats that don't match its rows; a failed checkpoint puts its ticks back for the next one. Leaving the app and both backups go through `_checkpoint_or_report()`, which logs and reports a failure (`session_checkpoint_failed`) and carries on: the settings flush, the stop-and-save of `on_stop` and the rest of the backup still run. A pending marker is set on the tick's row before it is recorded. The row is dated and named by the session's start (`SessionManager.started_at`, 0.0 before a start and after `reset()` → `checkpoint_session(started_at=…)` and `_make_session_name`), not by its first save a minute later. That logic is `theme.confirm_popup`, the one confirm (OK left, Cancel right); `_confirm_action` and History's delete confirm both call it. The session-end card ("Session saved") offers **Save notes** (`_on_summary_save_notes`, card stays open), **OK** (`_flush_summary_notes`: saves notes that changed since the last save — so an untouched card writes nothing and clearing saved notes clears them — stops the gong, closes) and a low-emphasis **Delete session** behind a confirm (`_on_summary_delete` → `_delete_sessions`, which closes the card once the session is gone — a failed delete leaves the card and its typed notes); `on_pause` and `on_stop` both flush the card's notes with the settings through `_flush_on_leave`, skipped while `_restoring`. `_summary_saved_notes` tracks the last written text. Notes go through the one `_save_session_notes(sid, notes=, tags=, mood=)` (also the diary's Save and its leave-flush): `DatabaseManager.update_session_notes` writes only the fields given and returns whether a row changed, failures `report_soft_error`, success `_toast("Notes saved")` and `HistoryScreen.update_session(sid, ...)` — the History model's session updated in place, not a dirty reload (that started the list from the top after every edit); `_update_item` re-derives that row's item, so its notes line appears, changes or goes (and the row's height with it) at once — `_toast` is the one toast (also the double-back "Press back again to exit"): `C.TEXT` on `paint_panel`, added to the `Window` so it shows above any open popup, on every platform; only while the app is leaving (`_leaving`, set by `_flush_on_leave`, when nothing the app draws is seen) it is the native Android toast. `_delete_sessions(ids)` is the one delete (a History row, the History selection, the end card): one `DatabaseManager.delete_sessions(ids)` transaction (metrics and rows, so an error deletes none of them; `delete_session(sid)` is a selection of one; then a `wal_checkpoint(TRUNCATE)`, since one big transaction parks every deleted page in the WAL, measured 40–100 MB for a few hundred long sessions, which it keeps until a clean close; a failed checkpoint — e.g. "database table is locked" while another thread's read is open on the shared connection — is only logged, since the delete has committed) on a worker thread — a large selection took 0.3–0.8 s on desktop on the UI thread — behind the loading overlay, modal at once and painted only if it runs past 0.15 s (`show_loading(text, delay=0.15)`: a tap in that first moment reached the rows and the end card being deleted), reporting `on_done(ok)`; a `sqlite3.Error` is reported as `session_delete_failed`; on success the end card closes (and its gong stops) if it shows a deleted session — a notes save there then failed with "no such session" — and `HistoryScreen.remove_sessions(ids)`, which removes those rows and model entries in place (see History list below) — no rebuild, no spinner, wherever the user is. History never lists the running session: its row exists from the first checkpoint, with that checkpoint's stats, and a History reload (on opening it while it is dirty — from launch, every ending and a profile delete until it is next opened) listed it with them, frozen there until the next reload; `_refresh_history` drops `_current_session_id` while `_session_pipeline_live()`, and `_finalize_stop_ui` marks History dirty, so the session appears once it ends. `_delete_sessions` also refuses it (`_current_session_id` among the ids while live): deleting it left the next checkpoints writing ticks for no session.

## Documentation Rules

**All documentation files must stay in sync with code changes.** When modifying features, UI, commands, architecture, or build process, update the relevant docs in the same commit or PR:

- `CLAUDE.md` — Architecture, commands, design decisions. Update when adding/removing modules, changing build process, or altering key patterns.

- `docs/USER_MANUAL.md` — English user manual. Update when UI flow, screens, or settings change.
- `docs/USER_MANUAL_UA.md` — Ukrainian user manual: mirror English manual changes.
- `app/assets/help/help_en.txt` — In-app help content (English). Update when features, connection flow, or settings change.
- `app/assets/help/help_ua.txt` — In-app help content (Ukrainian): mirror English help changes.
- `CHANGELOG.md` — Release history in Keep a Changelog format. Add entries under `[Unreleased]` as you commit; promote to a new version section when tagging.
- `IMPROVEMENTS.md` — Roadmap. Mark items as completed when implemented; add new ideas as they emerge.
- `pyproject.toml` — Ruff config. Run `ruff check app/ tests/ main.py` before every commit; all checks must pass.
